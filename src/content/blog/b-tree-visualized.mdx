## Where binary search falls short

In [Binary search, visualized](/blog/binary-search-visualized) we found a value among a billion sorted values in at most 30 comparisons. That is fast when the array sits in memory. A database index lives on disk, and there the cost that matters is not comparisons but **disk reads**.

A disk, even an SSD, reads data in pages of a few kilobytes. Each of the 30 jumps that binary search makes lands far from the last one, so each jump reads a different page. Thirty page reads per lookup is far too slow for a database that answers thousands of queries a second.

A B-tree fixes this by doing more work per page. Instead of one value per step, each node holds many sorted keys, and the whole node is one page. You read a node once, binary search inside it in memory, and follow one pointer down.

## How a node is laid out

A node with `k` keys has `k + 1` child pointers. The keys split the number line into ranges, and each pointer leads to the subtree for one range:

```
          [ 32 | 64 ]
         /     |     \
   < 32    32 to 64   > 64
```

Every key in the left subtree is smaller than 32, every key in the middle one sits between 32 and 64, and every key on the right is larger than 64. That rule holds at every level, which is what makes search work.

## Searching

Start at the root and repeat:

1. Read the node. This is one disk read.
2. Binary search its keys, exactly as in the [previous article](/blog/binary-search-visualized).
3. If a key equals the target, you are done. The key turns <Hl c="green">green</Hl>.
4. Otherwise, the search ends between two keys. Follow the pointer between them and go down one level.

If you reach a leaf and the key is not there, the tree does not contain it.

<TryCase client:visible widget="btree" run="search 50" label="Search for a missing key" />

```java
static boolean contains(Node node, int target) {
    while (node != null) {
        // Same binary search as before, inside one node.
        int lo = 0, hi = node.keyCount - 1;
        while (lo <= hi) {
            int mid = (lo + hi) >>> 1;
            if (node.keys[mid] == target) return true;
            if (node.keys[mid] < target) lo = mid + 1;
            else hi = mid - 1;
        }
        // lo is now the index of the child whose range holds target.
        node = node.isLeaf ? null : node.children[lo];
    }
    return false;
}
```

Search for a key that lives in the root or a middle level, such as 38 or 64. A B-tree stores every key exactly once, and some keys live in internal nodes, so some searches stop before they reach a leaf. Keep that in mind: the [B+ tree](/blog/b-plus-tree-visualized) changes it.

## Inserting and splitting

New keys always go into a leaf:

1. Search for the key as above, down to the leaf where it belongs.
2. Insert it into that leaf in sorted order.
   <TryCase client:visible widget="btree" run="insert 35" label="Insert into a leaf with room" />
3. If the leaf now has more keys than fit, **split** it. The middle key moves up into the parent, the keys left of it stay in the old node, and the keys right of it go into a new node.
   <TryCase client:visible widget="btree" run="insert 44" label="A full leaf splits" />
4. The parent gained a key, so it might be too full now as well. If it is, split it the same way, and keep going up.
   <TryCase client:visible widget="btree" run="insert 22" setup="insert 44; insert 70; insert 9" label="The split moves up to the parent" />
5. If the root splits, the middle key becomes a new root.
   <TryCase client:visible widget="btree" run="insert 42" setup="insert 44; insert 70; insert 9; insert 22; insert 59; insert 48; insert 2; insert 4; insert 65; insert 66; insert 41; insert 43; insert 6; insert 1; insert 3; insert 40" label="The root splits and the tree grows" />

<Callout kind="note" title="Trees grow at the top">
A B-tree never adds a level below the leaves. It only grows when the root splits and a new root appears above it. That is why every leaf is always at the same depth, and why no lookup is ever slower than the height of the tree.
</Callout>

Keep pressing <Hl c="green">Insert</Hl> in the widget, or <Hl c="green">Step</Hl> to pause on each split. Most inserts touch only one leaf. Every so often a split cascades all the way up and the tree gets one level taller.

A split also leaves both halves about half full. Each node is therefore between half full and full, apart from the root, so the tree never wastes much space and never drifts out of balance. Deletes have to keep that rule too.

## Deleting and merging

Deleting is inserting run backwards. Where an insert splits a node that gets too full, a delete repairs a node that gets **too empty**. With at most `m` keys per node, every node apart from the root must keep at least `m / 2` keys, rounded down. In the widget, with at most 3 keys per node, that minimum is 1.

1. Search for the key.
2. If it sits in an internal node, it cannot just be removed, because it separates two children. Replace it with its **predecessor**, the largest key in the subtree to its left. That key is always in a leaf, so now the key to remove is in a leaf.
   <TryCase client:visible widget="btree" run="delete 64" label="Swap in the predecessor" />
3. Remove the key from the leaf. If the leaf still has at least the minimum, you are done.
   <TryCase client:visible widget="btree" run="delete 61" label="The leaf still has enough keys" />
4. Otherwise, read a neighbouring node with the same parent. If it has a key to spare, **borrow** it through the parent: the separator between the two nodes comes down into the too-empty node, and the neighbour's nearest key goes up to take its place.
   <TryCase client:visible widget="btree" run="delete 82" label="Borrow through the parent" />
5. If no neighbour can spare a key, **merge**. The separator comes down from the parent, and the two nodes and the separator become one node.
   <TryCase client:visible widget="btree" run="delete 39" setup="delete 61; delete 63" label="Merge with a neighbour" />
6. The parent lost a key in the merge, so it might be too empty now as well. If it is, repair it the same way, and keep going up.
   <TryCase client:visible widget="btree" run="delete 67" setup="delete 82; delete 34; delete 80" label="Merge, then the parent borrows" />
7. If the root loses its last key, the merged node below it becomes the new root.
   <TryCase client:visible widget="btree" run="delete 8" setup="delete 82; delete 34; delete 80; delete 67" label="Two merges, and the tree shrinks" />

Borrowing goes through the parent because of the ordering rule. Delete 82 from the starting tree and its leaf is left empty. The left neighbour has keys to spare, but its 74 cannot move straight across, because the parent's 80 says that everything on the right is larger than 80. So 80 comes down and 74 goes up:

```
  before:       [ 80 ]                after:      [ 74 ]
               /      \                          /      \
    [ 67 | 69 | 74 ]  [ ]                [ 67 | 69 ]   [ 80 ]
```

Every key is still in order, and both leaves hold at least one key.

<Callout kind="note" title="Trees shrink at the top">
A merge never removes a level in the middle of the tree. The tree only gets shorter when the root gives up its last key to a merge, and then every leaf moves up together. Just like growth, shrinking keeps every leaf at the same depth.
</Callout>

The buttons in the steps above set up each case for you. To play the whole sequence by hand instead, press Reset in the widget, then press <Hl c="pink">Delete</Hl> with each suggested value in turn:

* **82, 34 and 80** each empty a leaf, and the leaf borrows through its parent.
* **67** empties a leaf whose only neighbour has nothing to spare, so the two merge. That leaves the parent empty, and the parent borrows from its own neighbour. Notice that a child pointer moves across along with the key.
* **8** sets off two merges in a row. The second one pulls down the root's only key, and the tree loses a level.

To see the predecessor swap, press Reset and delete 64, the root. Its predecessor, 63, moves up from a leaf to take its place. Use the <Hl c="pink">Step</Hl> button next to Delete to pause on each read, borrow and merge.

Real databases are lazier than this. Rebalancing after every delete costs extra writes, and a page that has just emptied is often filled again by the next inserts. InnoDB tries to merge an index page with a neighbour only once it falls below a fill threshold, `MERGE_THRESHOLD`, which defaults to 50%. PostgreSQL does not merge half-empty pages at all: `VACUUM` removes deleted entries later, and only pages that end up completely empty are taken out of the tree. A later article in this series will look at how each of them handles deletes.

## Fan-out is the whole point

Switch **Max keys per node** in the widget from 3 to 5. The same 14 keys now fit in fewer, wider nodes, and the tree is shorter. Real databases take this much further. MySQL's InnoDB uses 16 KB pages by default and PostgreSQL uses 8 KB pages. A 16 KB page holding 8-byte keys and pointers fits several hundred children per node. Call it 500:

| levels | keys reachable with about 500 children per node |
| --- | --- |
| 1 | about 500 |
| 2 | about 250,000 |
| 3 | about 125 million |
| 4 | about 62 billion |

The number of comparisons barely changes. Binary search inside a 500-key node takes about 9 comparisons, and four levels take about 36, which is what plain binary search would need over 62 billion values. What changes is the disk reads: 4 instead of 36. The root and the level below it are read so often that they stay cached in memory, so a lookup usually costs one or two reads from disk.

## What comes next

Databases rarely use this exact textbook structure. MySQL and PostgreSQL both build their indexes on a variant, the B+ tree, which keeps every value in the leaves and links the leaves together so that range queries such as `WHERE id BETWEEN 20 AND 60` become a single walk along the bottom of the tree. That is [the next article in this series](/blog/b-plus-tree-visualized).
